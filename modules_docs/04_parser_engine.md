**Module:** 04 - Parser Engine

**File:** `modules_docs/04_parser_engine.md`

**Version:** 1.0

**Status:** Implemented

---

# Purpose

The Parser Engine is responsible for transforming raw scanner artifacts into validated, normalized, scanner-independent domain models that can be consumed by the remainder of the platform.

It acts as the translation boundary between scanner-specific output formats and the platform's unified internal data model.

The Parser Engine ensures that every downstream module—including Asset & Vulnerability Management, Risk Engine, AI Engine, and Reporting Engine—operates exclusively on standardized domain objects rather than scanner-specific data.

The Parser Engine is the **only component** allowed to understand scanner output formats.

---

# Objectives

The Parser Engine is designed to achieve the following objectives:

* Isolate scanner-specific formats
* Normalize heterogeneous scan outputs
* Validate parsed data
* Build standardized domain models
* Produce a unified Assessment Package
* Maintain deterministic processing
* Support multiple scanners without modifying business logic
* Support future scanner plugins

---

# Responsibilities

The Parser Engine is responsible for:

* Receiving Scan Artifacts from the Scanner Engine
* Validating scan artifacts
* Selecting the appropriate parser
* Parsing scanner-specific output
* Validating extracted information
* Normalizing scanner-specific data
* Building platform domain models
* Packaging normalized findings
* Forwarding Assessment Packages to Asset & Vulnerability Management

The Parser Engine is **not responsible for**:

* Executing scanners
* Database persistence
* Risk calculations
* AI remediation
* Report generation
* Business decision making

---

# Design Principles

The Parser Engine follows:

* Single Responsibility Principle
* Parser per Scanner
* Deterministic Processing
* Scanner Independence
* Immutable Processing Pipeline
* Fail Fast
* Strong Validation
* Extensibility
* Loose Coupling

Business logic must never depend on scanner output formats.

# Parser Processing Pipeline

Every scan follows the same processing pipeline.

```text
Scan Artifact

↓

Artifact Validation

↓

Scanner Identification

↓

Parser Selection

↓

Data Extraction

↓

Validation

↓

Normalization

↓

Domain Model Construction

↓

Assessment Package Creation

↓

Next Module
```

Every stage has a single responsibility.

---

# Scan Artifact

The Parser Engine consumes only **Scan Artifacts** generated by the Scanner Engine.

A Scan Artifact contains execution information, including:

* Artifact ID
* Scanner Type
* Scanner Version
* Artifact Format
* Output Location
* Execution Metadata
* Execution Status
* Exit Code
* Processing Metadata

The Parser Engine loads scanner output using the information contained within the artifact.

---

# Artifact Validation

Before parsing begins, every artifact is validated.

Validation includes:

* Artifact existence
* Scanner support
* File availability
* Output format
* File integrity
* Execution status
* Required metadata

Invalid artifacts are rejected before parsing.

---

# Parser Registry

The Parser Registry maintains all available parser implementations.

Current parsers:

* Nmap Parser
* OpenVAS Parser

Future parsers:

* Nuclei Parser
* Nessus Parser
* Masscan Parser
* RustScan Parser
* Nikto Parser
* Gobuster Parser
* SSLyze Parser

Adding new scanners requires only registering a new parser.

---

# Parser Factory

The Parser Factory selects the appropriate parser using the Scan Artifact metadata.

```text
Scanner Type

↓

Parser Factory

↓

Scanner Parser
```

Business logic remains unaware of parser implementations.

---

# Parser Interface

Every parser implementation must provide a consistent interface.

Responsibilities include:

* Parse artifact
* Validate extracted data
* Return scanner-independent intermediate models
* Report parsing failures

Every parser returns the same internal representation regardless of the originating scanner.

---

# Data Extraction

The parser extracts scanner-specific information such as:

* Hosts
* Ports
* Services
* Operating Systems
* Vulnerabilities
* Scanner Metadata
* Execution Metadata

Extraction does not modify the data.

---

# Validation Engine

The Validation Engine validates extracted information.

Validation includes:

* Required fields
* Data types
* IP address validation
* Port validation
* Protocol validation
* Timestamp validation
* Severity validation
* CVE format validation

Malformed records are rejected.

---

# Normalization Pipeline

The Normalization Pipeline converts scanner-specific information into platform-standard representations.

Pipeline stages:

```text
Field Mapping

↓

Protocol Normalization

↓

Service Normalization

↓

Operating System Mapping

↓

Severity Mapping

↓

Timestamp Normalization

↓

Metadata Cleanup

↓

Domain Model Construction
```

Normalization ensures that downstream modules receive consistent data regardless of scanner origin.

---

# Domain Model Builder

The Domain Model Builder creates standardized platform models.

Typical models include:

* Host
* Asset
* Network Service
* Port
* Operating System
* Vulnerability
* Scanner Metadata

These models are scanner-independent.

---

# Assessment Package

Instead of returning multiple independent objects, the Parser Engine produces a unified Assessment Package.

The Assessment Package contains:

* Asset Inventory
* Network Services
* Open Ports
* Operating Systems
* Vulnerabilities
* Scanner Metadata
* Execution Metadata

The Assessment Package represents the complete output of the parsing process.

---

# Data Flow

```text
Scanner Engine

↓

Scan Artifact

↓

Parser Engine

↓

Assessment Package

↓

Asset & Vulnerability Management
```

No scanner-specific data leaves the Parser Engine.

---

# Scanner Independence

Downstream modules must never consume:

* XML
* JSON
* Scanner-specific severity scales
* Scanner-specific field names
* Vendor-specific terminology

Only normalized Assessment Packages may be consumed.

---

# Error Handling

Possible parser failures include:

* Unsupported scanner
* Unsupported artifact version
* Missing artifact
* Invalid XML
* Invalid JSON
* Corrupted artifact
* Validation failure
* Parsing failure
* Normalization failure

Errors are returned using structured parser exceptions.

---

# Logging

The Parser Engine should log:

* Parsing started
* Scanner identified
* Parser selected
* Parsing completed
* Validation failures
* Normalization completed
* Assessment Package created
* Unexpected failures

Logs should include:

* Scan ID
* Artifact ID
* Scanner Type
* Parser Version
* Processing Time

Raw scanner output must never be written to logs.

---

# Security Requirements

The Parser Engine treats all scanner output as untrusted input.

Security controls include:

* Artifact validation
* XML parser hardening
* JSON validation
* Input sanitization
* File validation
* Schema validation
* Size validation
* Secure parser configuration

The Parser Engine must never:

* Execute code from artifacts
* Trust scanner output blindly
* Execute embedded scripts
* Modify scanner artifacts

---

# Performance Considerations

The Parser Engine should:

* Parse artifacts efficiently
* Avoid duplicate parsing
* Stream large files where practical
* Minimize memory usage
* Produce immutable domain models

Performance optimizations must not compromise correctness or determinism.

---

# Version Compatibility

Parser implementations should support scanner versioning.

Example:

```text
OpenVAS 22.x

↓

OpenVAS Parser v1

OpenVAS 23.x

↓

OpenVAS Parser v2
```

The Parser Factory selects compatible parser versions when required.

---

# Extensibility

Adding support for a new scanner requires:

1. Implement Parser Interface
2. Register parser
3. Register supported versions
4. Add parser tests
5. Update parser registry

No existing parser should require modification.

---

# Dependencies

The Parser Engine depends on:

* Scanner Engine
* Configuration Module
* Logging Module

It communicates with:

* Asset & Vulnerability Management

It does not communicate with:

* Database
